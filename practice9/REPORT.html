Inspection and design choice

The form and the pure booking function each evaluated the same request. Extending the existing booking module lets one decision drive both availability and feedback.

Pattern rationale

In the repaired application, the booking module returned a Boolean while the form independently checked the same conditions to explain a rejection. Changing the maximum duration in only one place could therefore produce a correct decision with a misleading message. The refactor gives the existing pure module responsibility for selecting the first rejection reason. The form translates that reason into the same text students saw before, and existing callers still receive a Boolean from canBook. A request blocked for several reasons makes this separation observable because the first failure determines what the student sees. The fixtures all use start and end, and the checker has one booking policy. Both facts support keeping the design to one small module boundary.

Verification

The original project passed 34 tests. Before editing its implementation, four form tests were added to record the existing priority of validation messages. The same expanded suite passed all 38 tests before and after the refactor.
